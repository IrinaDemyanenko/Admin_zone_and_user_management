# Система взаимодействия с пользователем, с web-интерфейсом и REST Api.

### Перед вами часть проекта, касающаяся управления пользователями: систему регистрации и аутентификации, права доступа, работу с токеном, систему подтверждения через e-mail.

При подключении данной системы к проекту, учитывайте, что *модель User переопределена.* Обращайтесь к модели через get_user_model().  CustomUser дополнена полем ‘role’ – всего 3 роли (admin, moderator, user), для каждой роли своё разрешение (permission). Это разрешение можно подключить к любому view-классу или функции, тем самым ограничив доступ к данным, в зависимости от роли пользователя. Поле ‘email’ – обязательно, потому, как доступ к api и процесс восстановления пароля предполагают наличие действующего почтового адреса. Ограничение на модель: пара полей ‘username’ и ‘email’ должны быть уникальными – чтобы один и тот же пользователь, по рассеянности, не мог зарегистрироваться дважды.

*В проекте три приложения: users, api и additions.*

- Users – отвечает за всю часть, касающуюся управления пользователями: систему регистрации и аутентификации, права доступа, систему подтверждения через e-mail.

- Api - отвечает за те же ф-ии + работу с токеном (JWT + djoser).

- Additions - отвечает за служебные файлы, дополняющие код – кастомные страницы ошибок, контекстные процессоры, валидаторы, декораторы.

Доступно два варианта регистрации – через пользовательский интерфейс и через api.

Чтобы код можно было переиспользовать много раз, шаблоны и статика хранится на уровне приложения. Сейчас используются примитивные шаблоны, которые, при желании, можно заменить на собственные, подходящие к общему стилю сайта.

Делаем api открытым с помощью библиотеки django-cors-headers. Всем будут доступны адреса, подходящие под регулярное выражение r'^/api/v1/.*$'.

Для защиты приложения от недоброжелателей, устанавливаем лимиты (throttlings) на кол-во обращений к api:
 - для зарегистрированных пользователей : 1000 в день;
 - для анонимных посетителей : 100 в день.

Генерация документации для API, в формате OpenAPI 3.0., с помощью drf-spectacular. Документация доступна по адресам:
/api/v1/docs/redoc/
/api/v1/docs/swagger/

Выдача ответа API разделена по страницам (pagination), по 20 элементов на страницу.

Настроен почтовый сервер через аккаунт Google или Яндекс (нужный вариант раскомментировать).

Чувствительные данные (пароли) хранятся в файле .env. Чтобы почтовый сервер начал работать корректно, установите библиотеку dotenv в виртуальное окружение, создайте свой файл .env по образцу exempleenv.txt со своими данными.

*Основные адреса проекта:*
/api/v1/users/ - разрешает запросы только администратору сервиса (все действия с моделью User – получить, добавить, изменить, удалить);
/api/v1/users/<int:pk>/ - разрешает запросы только администратору сервиса (все действия с моделью User, но только для одного объекта – получить, добавить, изменить, удалить);
/api/v1/users/me/ -  каждый пользователь сможет по этому адресу прочитать или изменить свою запись в БД (только GET, PATCH запросы);
/api/v1/all-users/ - регистрация нового пользователя администратором сайта, разрешает только POST запросы только администратору сервиса;
/api/v1/all-users/<str:username>/ - каждый пользователь сможет по этому адресу прочитать, изменить или удалить свою запись из БД
/api/v1/auth/users/ - позволяет всем зарегистрироваться (POST запрос), разрешены безопасные методы GET, HEAD, OPTIONS, позволяет администратору посмотреть все записи модели CustomUser.
Для создания нового пользователя отправить запрос:
{
    "username": "*",
    "password": "*",
    "email": "123445@jf.com"
}
/api/v1/auth/jwt/create/ - разрешает только POST запросы зарегистрированным пользователям.
Отправив "username": "*", "password": "*" действующего пользователя, в ответ получаете два токена – access и refresh. Слово Bearer с access токеном нужно передавать в заголовке каждого запроса к api.
Отправить POST запрос, в теле указать:
{
    "username": "*",
    "password": "*"
}
